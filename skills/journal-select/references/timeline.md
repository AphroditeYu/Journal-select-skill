# 审稿周期与时间规划

## 先确定终点

询问具体截止日期和必须达到的状态：提交、接收、Online First、正式卷期或数据库检索。用户时区用于日期计算。不能将其中一个状态替代另一个。

## 时间证据分列

| 阶段 | 常见证据与限制 |
|---|---|
| 首次决定 | 可能含编辑拒稿；不能当外审或接收时间 |
| 外审后首次决定 | 若官网单独给出则记录，不与全部投稿首次决定混算 |
| 投稿到接收 | 核对是否包含作者修回、数据年份及样本范围；仅对接收稿统计不代表所有投稿 |
| 接收到上线 | 与投稿到接收分开；Online First 不等于有卷期 |
| 上线到检索 | 取决于数据库及状态，缺证据就写未知；On Hold 时尤其不能承诺 |

保留均值/中位数、单位、适用文章类型、数据年份和来源。不得从期刊年发文量推断录用率或时长。作者论坛经验仅为旁证，不混入官方统计。

## 排期方式

根据用户剩余时间，比较“直接投主要目标”和“先挑战再转投”两种顺序，需要时增加符合约束的替代方案。

总时间按不重叠阶段计算：准备 + 投稿到接收 + 接收到所需状态 + 转投/其他缓冲。若已使用官方投稿到接收指标，不再把包含在其中的修回重复相加。多个阶段的中位数之和只是粗略规划，不是总周期的统计中位数。

给出乐观、基准、延迟三种情景时，每个输入注明“官方观察 / 个案样本 / 用户估计 / 规划假设”。没有证据不得造三个精确区间；可以定性说明时限把握不足。至少考虑一次修回和一次拒稿转投的影响，但这是情景假设，不是必然会发生。

建议为准备、作者修回、转投和行政认定预留缓冲，数值依据用户实际情况并标为假设。可倒推“建议启动时间”，但不能称为保证赶上的最晚日期。

## 决策与触发点

- 若基准情景已超过期限，明确建议调整顺序或目标，不用乐观情景掩盖冲突。
- 若关键阶段未知，标“无法可靠判断是否赶上”，并列出需询问或查询的问题。
- 记录下一次复核时间或触发事件：准备正式投稿、收到大修、拒稿转投、发现收录状态变化。
- 可建议合理节点查询审稿进度；不能建议尚未正式撤回就在另一刊同时投稿。
- 历史统计和用户规划不能构成接收、上线或检索保证。
